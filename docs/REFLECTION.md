# HarnessAgent 项目反思

完成 HarnessAgent 后，我对 Coding Agent 的理解发生了明显变化。起初我更关心模型能否读写文件、运行命令并完成编码任务，后来才意识到，真正困难的部分不是让模型提出下一步，而是判断这一步是否允许执行、执行结果能否证明任务正确，以及程序中断后能否安全恢复。项目最终形成工程深度的地方，是把模型的不确定决策包在确定性的协议、权限、验证、持久化和恢复机制之中。即使移除真实模型，这些机制仍能由离线测试验证，这比一次表现良好的演示更能说明系统是否可靠。

Superpowers 对我最有价值的启发，是要求开发者先把问题说清楚，再拆分计划，并用失败证据约束实现过程。需求澄清促使我区分哪些事情可以由模型判断，哪些边界必须由程序保证；计划拆解让我开始记录依赖、涉及文件和验收方式；测试先行则把“应该安全”“应该能够恢复”变成可以重复判断的行为。不过，我不能把结果相似误写成流程合规。

测试先行在 AI 协作中总体上是放大器。模型很容易把“代码看起来合理”当成完成，而一个预期失败的测试能够把讨论收敛到客观差距。凭据改造时，我先规定环境中的明文值不能覆盖系统安全存储，状态查询也不能泄露秘密；旧实现先失败，修改后再通过。反馈闭环的测试还证明，验证失败会成为下一轮决策的输入，而不是只依靠提示模型自行检查。但测试也不是最终答案。公共契约尚未稳定时，测试可能固化错误理解；真实样例中也出现过测试全部通过而使用说明仍有错误的情况。因此，绿色结果必须与需求检查、真实场景和人工复核结合。

关于开发代理工作流，能够观察到的真实表现是：早期的跨文件任务会重复读取、修改失败、偏离需求，并在接近预算上限时才验证；加入固定任务目标、文件版本和有限恢复后，较复杂的任务能够在十余轮交互内完成并通过验收。回头看，现有计划中的一些任务仍然过大。更合理的颗粒度应当是一次只改变一个公共约束，先产生一个清晰失败，再在单次会话内完成验证。频繁修改核心循环和状态语义的工作应该串行，彼此独立的模块才适合并行推进。

设计规约和实现计划的质量直接影响模型是否会擅自猜测。一次陌生实现者检查暴露出两个典型歧义：开始修改前记录测试基线，并没有说明原项目测试失败时是否仍可进入修复；要求所有必要验证通过，也没有说明一个验证器都没有时能否直接判定成功。如果实现者按照集合的默认逻辑处理，可能让没有任何验证的修改被放行；如果把基线通过当成前置条件，又会阻止代理修复原本失败的项目。真实实验中，模型还曾加入需求没有要求的统计功能，最后由人工删除。这些经历说明，规约不能只写目标，还要明确失败路径、空状态和禁止事项，计划也不能只列文件，而应写出可观察的完成条件。

最有效的上下文策略不是不断增加长提示，而是让信息保持稳定、相关并且及时。原始任务、验收条件和禁止事项需要固定保留，历史对话可以裁剪；每轮还应提供当前阶段、合法的下一步、工作区版本、近期失败证据和剩余预算。文件发生变化后，代理应重新读取真实内容，而不是依赖旧上下文继续猜测。补齐结构化协议和动态状态后，同类只读任务从九轮降到两轮，耗时也从约一百秒下降到十余秒。这让我认识到，上下文工程的重点不是“给得更多”，而是让模型在当前时刻看到足以作出合法决策的最小证据。

凭据和分发要求迫使我补齐了原本容易忽略的产品闭环。如果没有这些要求，我可能会把密钥留在被忽略的明文文件中，并把“本机可以运行”误认为完成。经过威胁分析后，真实凭据被收敛到操作系统的安全存储中，录入时隐藏输入，查询、异常和运行记录不显示明文。分发方面，我也认识到成功构建安装包不等于别人能够获得它。依赖声明、命令行入口、隔离安装、持续集成、版本发布和目标机器上的安全配置缺一不可。

我对 Superpowers 的最终看法是，它假设任务能够清晰拆分、版本控制成本足够低、测试可以充当可靠信号、新代理能够依靠文档恢复上下文。这些假设在独立模块上较成立，在多个任务同时修改核心状态时并不完全成立。过度并行会增加冲突，过细拆分也可能丢失整体语义。它真正有价值的不是流程名称，而是迫使开发者留下问题定义、失败证据、评审记录和人工决定；至于做什么、是否真正做对，责任最终仍然属于人。
